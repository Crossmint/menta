# Engineering design

How Menta fits together. The [README](../README.md) covers what Menta is, its goals and setup; [HOSTS.md](HOSTS.md) covers each assistant host and [ADDRESSES.md](ADDRESSES.md) saved addresses.

## Languages

The web app speaks English, Spanish, French, German, Italian, Brazilian Portuguese, Dutch, Polish, Hindi, Japanese, Korean and Simplified Chinese (`apps/web/lib/i18n/locales.ts`). There's no i18n library: messages are typed objects, `messages/en` is the source and every other language must have its shape (the compiler checks keys; `messages.unit.test.ts` checks placeholders). `{name}` placeholders are filled by `format`, counts by `plural` (Intl.PluralRules), and sentences with links by `rich`.

`proxy.ts` decides each page's language and passes it on as the `x-menta-locale` request header: the homepage has one URL per language (`/` for English, `/es`, `/ja`…) and `/` redirects to the visitor's; every other page keeps its URL and uses the `menta_locale` cookie (set by the language picker) or else Accept-Language. The root layout sets `<html lang>` and provides the messages to client components (`useI18n`); server components call `getI18n`. Dates, money and country names use Intl with the page's language. Not translated yet: the web chat and checkout dock, the shared checkout UI in `packages/agent/src/ui` (also the in-host card), and model-facing text (the agent answers in the user's own language).

## Request flow

The main Eve agent uses Claude Haiku 5.5 through AI Gateway with Anthropic adaptive thinking and medium effort. Composer predictions separately use Haiku with thinking disabled and low effort. Crossmint's checkout browser remains responsible for merchant shopping.

`agent/instructions/current-time.ts` supplies the live UTC clock through Eve's dynamic instructions on every `turn.started`, rather than baking a date into the build. Relative event requests use that clock and the event's local start time; instructions require checking an official schedule, excluding past dates even when stale search snippets call them "next", and preserving the future-event requirement in the checkout task.

1. The browser talks to Eve's routes (`/eve/v1/*`) on the same origin. `channels/eve.ts` verifies the HttpOnly Stytch session cookie on every request and checks that the session belongs to the caller. Creating a session binds it to the user in Neon, with the first message as its title (the sidebar lists these).
2. The agent's checkout tools act as the signed-in user: the Stytch user ID becomes `x-crossmint-user-id` on Crossmint server-key calls.
3. After starting a run the agent calls `watch_checkout`, an Eve task that polls Crossmint durably until the store needs the user or the run ends, then wakes the model.
4. The chat polls `/api/checkouts/[runId]` for each run it mentions (the same Crossmint read, scoped to the user). Where a run starts there is a one-line row that opens its card; while it is active, a dock on top of the composer shows it (the one that needs the user most, with a switch when there are several): status, live view, cancel, and whatever the store is waiting on. When it settles, its outcome card lands where the conversation is. The live-view URL reaches only the signed-in user's browser; `toModelOutput` strips it from model context. Progress: that route (and the MCP `card_checkout` the in-host card polls) also reads the run's messages (`GET /runs/:id/messages`, oldest first, read forward from a cursor) and adds `progress` to the view: Crossmint's newest buyer-safe step line and the last five steps. Each instance keeps a small per-user, per-run log with the page's `streamCursor`, so a refresh of an active run costs one extra call (ended runs read nothing); a failed read only drops progress. The dock's header, the checkout card and the in-host card show the newest step ("Still working…" once it is old), and the live view lists the recent ones; `forModel` strips it, and the MCP result carries it only in `_meta["oca/progress"]`. The resumable SSE stream (`/messages/stream`, resumable from the same cursor) can replace polling later.
   Which run the dock shows is one rule (`packages/agent/src/dock.ts`, `@oca/agent/dock`).
5. Store questions, protected inputs and payment approval are completed in the dock, with Crossmint's React components for the private parts, loaded with the client key and the user's Stytch session JWT (Crossmint's project trusts Stytch as a JWT provider). Payment approval is our own saved-card list and Approve button (`useCardApproval` in `@oca/agent/approval`, shared with the ChatGPT/Claude card): our server lists the user's cards (Crossmint's list route doesn't answer browsers) and enrolls them for agent payments with the user's email; the click creates the order intent for the chosen card, and Crossmint's `OrderIntentVerification` or `CrossmintCvcRecollection` runs when its rail asks; "Add a card" is `CrossmintPaymentMethodManagement` in new-card mode. Wallet's "New approval" reuses the same flow (`ApprovePayment`) for an approval the user describes themselves: an amount in any market's currency, a name (the order intent's description), an optional store (the merchant; Crossmint's API leaves it optional) and an expiry (a week, a month, a year or a chosen date). Nothing about it is stored in Menta; Wallet shows the store's icon, or a placeholder. It yields an `orderIntentId`; `CrossmintProtectedInput` yields `protectedInputId`s; ordinary fields are plain values. Our server submits them to the run, and the dock posts a chat message naming the checkout ("Answered the store in the checkout panel (checkout … at …):" with one line per answer, or "Approved the payment in the checkout panel (…)") so the agent resumes watching that run, or, once a cancel there succeeds, "Cancelled the checkout in the checkout panel (…)." so the agent confirms and stops (a note still waiting to go out for that run is dropped); the conversation shows each as one quiet "You answered <store> · …" line. `/checkouts/[runId]` does the same on its own page for links from ChatGPT, Claude and Grok Bot (`via=chatgpt|claude|grok`: a "From <assistant>" badge with that assistant's app icon, and for Grok Bot, which has no documented link to open it, a "Return to Grok Bot" line instead of a Back button); returning from it sends "I finished the secure step." Its link previews are generic ("Approve your checkout · Menta", no item, price, store or user), because assistants and messengers unfurl the URL from their servers.

The user's assistant picks which spending limit pays (`packages/agent/src/limit-payments.ts`). A spending limit is a Crossmint order intent: the user approves an amount on one of their cards, and it can pay several checkouts until it runs out or expires. When a checkout reaches its card payment, the step's `next` line tells the assistant to read `spending_limits` (each limit's id, the name the user approved it with, what's left, its store or none, and expiry; never a card number, token or card ID) and to call `pay_with_spending_limit` with the one whose name fits what the purchase is for; if none fits, it asks for a generic one (`request_spending_limit`) or the user approves one in the card, dock or secure page, as before. The web chat has the same two tools. Both mint the user a five-minute Stytch session server-side (the same one as the card's secure step; Crossmint's order-intent API takes only a client key and a user session) and are offered only where the Trusted Auth Token profile is configured. Before paying, Menta checks the pick: the user's, active, unexpired, its card able to pay now, the payment's currency, enough left, and any store or the payment's store (Crossmint's reuse rule); otherwise the tool refuses and says why. A payment request takes one answer: every payer (the assistant's pick, and the user's approval in the dock, card, secure page or request page) uses the same message ID for it (`paymentMessageId`), which Crossmint refuses with a different body, and the tool first checks the run's messages on Crossmint and never answers a request someone already answered. Reads never pay: nothing is paid until the assistant or the user acts. The model never creates, approves or raises a limit.

Making a spending limit is one form (`apps/web/app/_components/limit-form.tsx`), in Wallet's "New spending limit" modal and on the request page: the amount, then rows for the purpose (shown as "Purpose"; the API field is still its name), currency, where it works (any store, or one store with its icon), when it expires (a week, a month or a picked date) and the card, then Crossmint's Approve. The request page, `/spending-limit/<token>`, is a limit an assistant asked for, built like the secure page (the assistant's icon and name, the details prefilled and editable, Powered by Crossmint), under "Set how much {host} can spend on your card, for this order and the next ones. Revoke it any time."; the in-host card says the same with "your assistant"). The link holds no details: the token is the request sealed with AES-256-GCM under a key derived from the Stytch secret, bound to the user and good for 24 hours (`packages/agent/src/limit-requests.ts`), and `/api/spending-limit-requests/[token]` opens it only for that signed-in user. Menta stores nothing about it. With a checkout in it, the approved limit pays that checkout's open payment. Assistants make these links with `request_spending_limit` (MCP, `src/mcp/limit-tools.ts`, registered where the server has `STYTCH_SECRET`; the web chat's own tool in `agent/tools/`): the model gives a generic name, amount, currency, expiry and optionally the store and a checkout of the user's, and gets back the url and a `next` line. The tool only seals a request; nothing is approved until the user does it on the page. The MCP server also links a checkout's payment step there: where the key is set, `linkPaymentsToLimits` turns the payment's `pending.actionUrl` into a request for that payment (its amount and currency, its store, a week, named "<merchant> order", the checkout's `runId` and the host as `via`), so a host without our card, and our card's "Set up a spending limit" link, get the new approval design, and approving it pays the checkout. The card accepts that link only for a payment, and a token sealed anew on each read doesn't count as a change for its idle pause. Where the model reads the step as text (no card, no URL elicitation), its `next` line instead asks it to call `request_spending_limit` with the `runId` and a generic name for that kind of spending ("Food delivery", not the product or store) and an amount of at least the payment, so the limit is one the user can reuse; the server's link is the fallback if the call fails. With a `runId` whose payment is open, the tool refuses another currency, an amount below the payment or another store, seals the checkout's store for the page's "It pays for … right away" line (the limit itself can work anywhere) and tells the model to keep following the checkout; the page pays the checkout only with a limit that covers it (currency, amount and store). The form shows under the card row, before Approve, who never sees the card ("Your card stays with Crossmint. Grok Bot never sees it."). Questions and private details keep the secure page.

The card network's check runs on the limit being approved: Crossmint only verifies a rail on an order intent, never at registration, so adding a card makes no check. When the check fails or is closed, the limit still goes through with Crossmint's encrypted card (the `encrypted-card` rail Agent Checkouts uses), with no error screen, and Menta records the card as `encrypted` in Neon `card_setup` (migrations/0016), so its later approvals skip the check. Crossmint has no field for it.

Addresses in the chat ([ADDRESSES.md](ADDRESSES.md) is the model): the agent settles a delivery's address in the conversation before `checkouts__create`, with `checkouts__addresses`, `checkouts__save_address`, `checkouts__delete_address` and `checkouts__set_default_address` (the same helpers as the MCP tools, `address-chat.ts`). Only a delivery to someone else with no saved address doesn't start: `checkouts__create` returns `needs_address` and the model asks for it in chat, saves it and starts again. A label that only resembles saved ones returns `which_address` and the agent asks in one line. The new-chat screen shows "Add a delivery address" while the user has none; it opens the account form in a sheet and saves the user's own place as the default.

Composer predictions: after Eve finishes a reply, or when the checkout shown in the dock asks an ordinary question, `POST /api/predictions` predicts one short user reply with Claude Haiku 5.5 (no tools, thinking disabled, low effort, 5-second context-and-generation budget). Predictions aim for the user’s likely direct answer, allowing ordinary preferences and choices to be inferred from the current request, memory and offered price or convenience rather than requiring an explicit prior answer. Replies match the user’s brevity; unknown personal facts, unsupported budgets and secure-step answers are withheld. The conversation composer keeps “Message Menta” as its fallback while Eve works or waits, leaving progress and checkout questions above it. A prediction replaces that fallback with a 180 ms fade and 4 px upward motion, together with its accept action (no animation with reduced motion), only while the composer is empty; Tab or Use suggestion fills the draft, Escape dismisses it until the next reply or question, and Send is still required. Accepting keeps the suggestion cached, so clearing the draft shows it again. The dock reports its selected run, so switching runs follows the question actually on screen; answered or cancelled requests stop contributing. Context is at most six visible text messages, retaining the latest user request even after many agent updates (a photo-only request stops the scan without reviving an older goal), plus the current question and choice labels and up to 8,000 characters of saved memory plus up to 100 saved address labels, places and default flags read on the server for the verified user (current requests override memory; failed memory or address reads independently fall back to the available context), with links removed; no tool outputs, photos, provider option values, progress, saved address streets/contact details/profile IDs, or payment/protected/sensitive requests reach the predictor. On mobile the composer uses two rows: text above the photo, plain-text Use suggestion, dictation and send controls. Desktop keeps the controls inline and shows a plain Tab hint. Predictions pause for dictation and attachments. The client memoizes context and reads the latest six visible messages and scans only roles farther back if needed to retain the latest user request; requests settle for 150 ms, never follow typing, and time out after five seconds. Memory and address reads run in parallel with individual 750 ms budgets, keeping whichever source is ready. The signed-in, same-origin route is uncached, allows 20 calls per minute per user per instance, and fails quietly in the composer. Server logs distinguish generated drafts, abstentions and oversized output without logging text; generation errors return 503 (504 on cancellation) and log only a fixed category and numeric upstream status, never the raw SDK error. A changed question or conversation aborts and discards the previous request.

Voice input: the composer's mic asks `POST /api/transcription` (signed-in, same-origin, 30 starts per user per 10 minutes per instance) for a 60-second AI Gateway client secret bound to `microsoft/mai-transcribe-2-streaming`, then streams 24 kHz PCM from an AudioWorklet straight to the Gateway's transcription WebSocket with the AI SDK's `experimental_streamTranscribe`. Partial text is written into the composer as the user speaks; nothing is sent until they press Send. Recordings stop at 2 minutes. Audio and transcripts never reach our server or logs.

Photos: the composer turns each picked, pasted or dropped image into a JPEG no larger than 1600px on its long edge (re-encoded at lower quality above 700 KB) and sends it as an inline `data:` file part with the message through Eve, so no upload storage is needed. Four photos keep the request under Vercel's 4.5 MB body limit. HEIC that the browser cannot decode goes through `heic-to` (libheif, LGPL), loaded only on that path. Eve keeps the photo in the session history, so it shows again when the conversation reloads. Eve also copies every attachment into the session's sandbox and reads it from there on later model calls. The agent runs no commands, so the sandbox exists only for this: just-bash locally, Vercel Sandbox (network off) on Vercel, where a function has no lasting local disk.

Location: when an order depends on where the user is ("nearest Starbucks", "pickup near me") and they named no place, the agent calls `request_location` (`agent/tools/request_location.ts`), a workflow tool that pauses the turn with `ctx.ask` (options `location-shared` / `location-unavailable`, no free text, so a typed message steers and withdraws it; it gives up after 2 minutes). The chat sees the open request in Eve's input ledger (`openConversationInputs`), calls `navigator.geolocation.getCurrentPosition` (the browser's prompt is the only UI), posts the coordinates to `POST /api/location` (signed-in, same-origin, 20 per user per 10 minutes per instance), which reverse-geocodes them with OpenStreetMap Nominatim (`lib/server/geocode.ts`: contact User-Agent, one request per second per instance, 3-decimal cache for 6 hours, 8 s timeout, coordinates never logged) and returns only `{ neighborhood, city, region, postalCode, country }`. The chat answers with `respond([{ requestId, optionId, text }])`, the place as JSON text; the tool validates it and returns `shared` or `unavailable` with a reason. The model never sees coordinates. A place shared earlier in the conversation answers a repeat ask without asking the browser again, and the instructions tell the model to reuse it. The conversation shows it as a step ("Getting your location…", "Got your location: Brickell, Miami" with OpenStreetMap attribution, "Couldn't get your location"). No IP geolocation: many users run VPNs. Checkout creates send `browser.location = { type: "country", countryCode }` from the model's `country` or the attached address; a 400 that names the browser location is retried once without it.

The model never sees card data, protected values or approval controls. The user can also answer ordinary store questions (`handling: standard`) in chat; the agent relays them with `checkouts__answer`.

## MCP flow

The host shops, we buy. ChatGPT and Claude already search and browse, so `{OCA_WEB_ORIGIN}/mcp` gives their model ten tools, not a second agent (`src/mcp/server.ts`):

| Tool | What it does |
| --- | --- |
| `start` | Starts a checkout (`storeUrl`, `task`, `maxCost`, `country`, and the shipping fields: `fulfillment`, `deliverTo`, `addressLabel`, `cityHint`) and follows it. |
| `answer` | Sends the user's answer to the store's open question (`answers`, or their own words as `text`); with nothing open, `text` steers the run. Then follows it. |
| `continue` | Follows a running checkout (`afterRequestId`: the step the user just finished). |
| `cancel` | Cancels it. |
| `history` | One checkout by `runId`, or the user's recent ones (`cursor` pages). Read first, so the model never starts a second checkout for the same thing. |
| `delivery_addresses` | The saved delivery addresses (complete, with IDs and the default), and a `next` line: say where it goes, ask which one, or ask for a new one. |
| `save_delivery_address` | Saves an address the user gave in chat, or changes one by `id`; `makeDefault` for the user's own place only. An empty email is the user's own. |
| `delete_delivery_address` | Deletes one by `id`, when the user asks. |
| `set_default_delivery_address` | Makes one of the user's own places the default, or `null` for none. |
| `manage` | Links to `/wallet` (cards) and `/addresses`. |

Plus `grok_bot_updates_setup` for Grok Bot only and the app-only card tools (`src/mcp/card-tools.ts`). They are thin wrappers over `createCheckouts` (the same Crossmint calls as the web), served by the official MCP SDK (`@modelcontextprotocol/server`, `createMcpHandler`) from a Next route handler: stateless, one server instance per request, 2026-07-28 plus the 2025 Streamable HTTP fallback.

Moments (`src/mcp/moments.ts`): the assistant speaks when it has something to tell the user, and only then. `start`, `answer` and `continue` read the run every 2 s (`src/mcp/wait.ts`) and return as soon as the store needs the user (a question, private details, a payment to approve), the run ends, or the call's window is up: 200 s for Claude, ChatGPT and local dev (Claude cuts a call at 240 s, ChatGPT at 300 s), 50 s for everyone else (Codex defaults to 60 s). So the turn ends on the moment with one new assistant message, which is what makes the native apps notify the user, and nothing is said in between. A window that runs out returns "still working" and a `next` line to call `continue`. The request's abort signal ends the wait of a client that hung up. The route allows 240 s (`apps/web/app/mcp/route.ts`).

Each result is `{ checkout, next }`: the Crossmint view with the live-view URL and progress stripped (`forModel`) and one line telling the host what to do (`nextStep`). The server `instructions` are short: confirm item, store and price ceiling, settle a delivery's address first, call `start` once, let the tools follow, payments come only from spending limits the user approves, never start a second checkout. `pnpm plugin:sync` copies them into the buy skill; a unit test checks the drift.

Addresses: a delivery to someone saved goes by `addressLabel`. A label that only resembles saved ones returns `{ whichAddress, next }` and the model asks in one line. Someone else with no saved address returns `{ addressNeeded: { label, cityHint }, next }` on every host: the model asks for it in chat, saves it with `save_delivery_address` and calls `start` again. No form, card or link; the card only points at the chat.

A checkout is a conversation in ChatGPT and Claude: one new assistant message per moment, not one card that changes.

| Moment | Message | Card |
| --- | --- | --- |
| Start | "Starting your checkout on Amazon." | none: `start` follows the checkout to the first thing that needs the user |
| Store question | "Amazon has a few options. Pick the one you want." | step card (`"step"`): the dock's picker with Choose per option, fields, "Something else…" |
| Payment or private details | "Ready to pay $10.27 at Amazon. None of your spending limits covers it, so approve one in the card." | step card: for a payment, "Set up a spending limit", a link to the spending limit request page; for private details, Crossmint's protected inputs (or "Fill it in on Menta") |
| Done | "Order placed · <order number>" (or the failure or cancel line) | the receipt (other endings: text only, no card) |

- The card is drawn only by `show_checkout_step` (model-visible, card hosts only), which the `next` line asks for at a store question, a payment that no spending limit of the user's fits, private details, and an order with a receipt (other endings are text only). `start`, `answer` and `continue` are text-only: they follow the checkout and return when something needs the user. So there is no card while a checkout starts or works, only for the moments the user acts in, and the receipt.
- `show_checkout_step` takes an optional `language` (the language the assistant writes to the user in, e.g. `es`, `pt-BR`); the card writes its own text in it, ahead of the host's locale, and it never picks anything but UI text.
- When the user acts in a step card, the card answers through the app-only `card_answer` (which doesn't wait) and says what they did as the user (`ui/message`, else ChatGPT's `sendFollowUpMessage`, else model context): "Answered amazon.com in the checkout card: Feather wand." An assistant-only note adds the runId and `afterRequestId`, so the model calls `continue`. No values from protected fields or cards, ever.
- When the payment a step card showed moves on, the newest card for the run asks `card_checkout` with `paidFor` (its requestId) whether a spending limit paid it (`checkouts.answer`, from the run's messages on Crossmint; a decline or the user's other words also move a checkout on). Only then, and only if one of its own reads after it loaded still had that payment open (so a reloaded or replayed card never does), it puts the note in model context and says once, as the user: "I set up a spending limit on Menta and it paid the <store> checkout".
- If the user answers in chat instead, the model sends it with `answer`.
Checkout card (MCP Apps, SEP-1865): `show_checkout_step` carries `_meta.ui.resourceUri` (plus ChatGPT's `openai/outputTemplate`), so ChatGPT, Claude and other MCP Apps hosts render the card with the tool result; text-only hosts (Codex, Grok Bot) keep using `content`/`structuredContent`. The card shows only when the user must act (a store question, private details, a spending limit for a payment) or for a receipt; there is no view of every checkout in the host. For a checkout in progress the user asks the assistant (`history`); Activity lists only purchases.

Cards only where they are drawn (`src/mcp/clients.ts`): every request knows whether its client draws our card, and `createCommerceServer({ cards })` words its results to match. Grok Bot (xAI's desktop agent, clientInfo `Cursor` 1.0.0, protocol 2025-11-25, `capabilities: { elicitation }` and no MCP Apps extension) once told its user to "pick one on the card below" when nothing was drawn. The rule: a host we identify (ChatGPT, Claude, local dev) draws cards. Otherwise a 2026-07-28 request's own `_meta["io.modelcontextprotocol/clientCapabilities"]` decides (the `io.modelcontextprotocol/ui` extension, ext-apps `EXTENSION_ID`). A 2025-era client declares capabilities only at `initialize`, which the endpoint sees (authenticated) before the stateless server does; it records the answer per OAuth `client_id` (the token's signed claim) in Neon `mcp_clients` (migrations/0005: client ID, `draws_cards`, `updated_at`; no secrets) and a per-instance cache (10 minutes; unknown clients aren't cached, so an `initialize` on another instance is seen), and the client's later requests read it. Never seen: no cards. Without cards no model-facing text mentions one: store questions say to ask in one short message (or the host's own picker), listing the options exactly as given, and to send the answer with `answer`; payment and private details say to give `pending.actionUrl` exactly as returned, never to collect secrets in chat, and then to call `continue`. Someone else's new address is asked in chat on every host. Native forms are unchanged: 2026 clients without cards still get them, 2025 clients never do. The server `instructions` (and so the buy skill) describe both cases. The MCP route logs each `initialize`'s client name, capability and extension keys and elicitation modes, and whether tool calls carry a `progressToken` (a flag only). The `initialize`'s `clientInfo.name` (100 characters at most) is recorded with `draws_cards` (migrations/0006 adds `client_name`): a 2025-era client named `Cursor` without MCP Apps is Grok Bot (`isGrokBot`; Cursor's IDE names itself differently and draws cards, and 2026-07-28 requests carry no clientInfo, so they never count). Grok Bot later started declaring the MCP Apps extension while never reading the card resource, so the sign-in decides too: an OAuth client whose Stytch-registered redirect URLs include one under `https://www.cursor.com/agents/` and no `cursor://` one (`createCursorAgentResolver` in `hosts.ts`, cached an hour per client) gets no cards, and named `Cursor` it is Grok Bot. The token's signed `client_id` names the OAuth client. A Dynamic Client Registration client is classified by its redirect URLs from Stytch. Those come from Stytch's record (`client_id_metadata_url`, `redirect_urls`) or, when Stytch can't return it, from the document itself (fetched only from those domains, no redirects, 64 KiB, 3 s, and it must name itself as `client_id`). Claude Code's claude.ai document lists loopback redirects, so it stays unknown, like Codex. Each re-reads the run and checks that the open request is protected and has this `requestId`. `answer` and `card_answer` still refuse payment and protected requests.

ChatGPT derives its stable `*.web-sandbox.oaiusercontent.com` origin from `openai/widgetDomain = origin`. The Crossmint client key must allow each card origin (exact match). `card_secure_session` logs the requesting card origin to make that easy to find.

It links out ("Fill it in on Menta", `/checkouts/[runId]`) on: no credentials, the script failing to load, a `securitypolicyviolation` for our script or Crossmint/Basis Theory URLs, no answer from Crossmint within 15 s, a render error, or a failed send. MCP Events (ChatGPT Work chats, dots): ChatGPT can subscribe to a checkout and hear when it needs the user or ends, without polling. We implement the webhook mode of the [draft MCP Events spec](https://github.com/modelcontextprotocol/experimental-ext-triggers-events/blob/main/docs/design-sketch-proposal.md) as [OpenAI documents it](https://developers.openai.com/plugins/build/mcp-events) (`src/mcp/events.ts`). The MCP SDK (2.3.1) has no events support, so the server adds the `events` capability and its three custom request handlers itself, only on 2026-07-28 (`server/discover`) instances: 2025-era clients and anyone who doesn't subscribe see exactly the server they did before.

- Events (`events/list`, all `delivery: ["webhook"]`, optional `runId` filter; without it, all of the user's checkouts including later ones): `checkout.needs_you` (a store question, private details or a payment ready to approve), `checkout.order_placed` (receipt total and store order number when captured) and `checkout.ended` (canceled, couldn't buy, stopped, or `mayHaveOrdered` when the order may have gone through). `data` is model context, so it is data only: `runId`, `store`, `task`, the status label and `headline` exactly as the dock shows them ("store.com · Ready to pay", "Needs your answer", "Needs a secure step", "Order placed", "Couldn't buy · Item unavailable", "Stopped", "Canceled", "Not confirmed"), the card's outcome line as `detail`, the payment's `amount` and "Exact amount to Store" note, the store's question and fields (so the model can answer with `answer`), and `url`, the signed-in `/checkouts/[runId]` page (`via=chatgpt`). Never the live view, progress, addresses or instructions; a payment event only tells the user where to approve. A unit test checks the copy against the card's rules.
- Subscribe (`events/subscribe`): the user comes from the Bearer token only. We validate the name (`-32011`), mode (`-32014`), arguments and the `whsec_` secret (24 to 64 bytes) and the callback URL (`-32602`: https on 443, no credentials, no internal names or non-public IP literals), check that a filtered `runId` is the user's (`-32012`), cap 20 live subscriptions per user (`-32013`), and verify the callback once per user and URL per 24 hours with a signed `verification` challenge it must echo (`-32015` with the reason category otherwise; at most 10 challenges per user per 10 minutes per instance). The ID is `sub_` + SHA-256 over (user, URL, name, canonical arguments), so a repeat subscribe is a refresh. We grant at most 2 minutes (`refreshBefore`, at least 1 minute, never no-expiry) and return `cursor: null` (no replay). A refresh with a new secret keeps signing with the old one too for 5 minutes. `events/unsubscribe` deletes the user's matching subscription and always returns `{}`.
- Change detection, without a job runner or cron: Crossmint has no run webhooks, and Eve can only start durable work inside a model turn, so we use the two moments the protocol and our own traffic already give us. (1) Every refresh, which the client must send before `refreshBefore` to keep the subscription, reads the covered checkouts from Crossmint and delivers what changed: the short grant makes ChatGPT's refresh the poll, at no cost when nobody subscribes, and it stops when ChatGPT stops. (2) Every read of a checkout for that user on any of our surfaces (MCP tool calls and the card's polling, the web dock's and secure page's `/api/checkouts/[runId]`) passes the view it already has to `observe`, which is how a payment approved on the secure page or a question answered in the card turns into an event within seconds. Per subscription we keep only `seen` (run → last state key, `status:requestId`), so each change is sent once; a new subscription records the current state first ("start from now"), and a run first seen later is news only if it started after the subscription. Background work runs in Next's `after()`.
- Delivery (`src/mcp/webhooks.ts`): one POST per event, `{ eventId, name, timestamp, data, cursor: null }`, serialized once and signed per Standard Webhooks (`webhook-id` = `eventId`, `webhook-timestamp`, `webhook-signature: v1,<HMAC-SHA256 over id.timestamp.body>`) plus `X-MCP-Subscription-Id`. `eventId` is stable per subscription, run and state, so retries and repeat checks dedupe at the receiver. Up to 3 attempts per check (408, 425, 429, 5xx and network errors, 1 s then 3 s apart); after that the event stays pending and the next check resends it with the same ID and a fresh signature. 410 and 413 drop it. Outcomes are recorded as the spec's categories and returned on refresh as `deliveryStatus`. The transport is node:https to the hostname (TLS verifies it) with a resolver that refuses any non-public address (IANA special-purpose ranges; IPv6 must be global unicast) at connect time, a 10 s deadline, no redirects and 64 KiB of response read.
- Storage: `mcp_event_subscriptions` in Neon (migrations/0004): user, event, run filter, callback URL, host, the signing secret(s) sealed with AES-256-GCM under a key derived (HKDF) from `STYTCH_SECRET`, expiry, verification time, `seen` and delivery status. Rows expired for a day are purged on the next new subscription. Secrets are never logged; logs name only the subscription ID, event and failure category. If `STYTCH_SECRET` changes, stored secrets stop opening and deliveries wait for the next refresh, which carries the secret again.
- Ending a watch: a subscription filtered to one checkout ends 10 minutes after that checkout ended (and its event went out). The next refresh is refused with `-32012` (`data.reason: "checkout_ended"`) and the row is deleted, so ChatGPT stops refreshing and we stop reading Crossmint for it. ChatGPT supports no `terminated` envelope, so the refused refresh is the signal. A new subscription to a checkout that already ended is refused the same way (it could never fire, and it stops a client from re-subscribing in a loop).
- Access: a disconnected assistant can't refresh (its token stops working within the token lifetime), so its subscriptions lapse within 2 minutes of the last refresh.

Grok Bot updates (`src/mcp/grok-bot.ts`): push for Grok Bot. It has no MCP Events or cards, but a Grok Bot routine can start from a webhook: a URL plus a key, sent as `Authorization: Bearer <key>`, with a JSON body "the Bot receives … with the routine instruction" (cursor.com/help/grok-bot/routines; a 200 means a run started). Grok Bot notifies the user on desktop and phone when a run needs them. When the user finishes something on our site that Grok Bot sent them to (approving a payment, entering private details) or answers elsewhere, the run goes from `awaiting_input` back to working, and the follower pushes `checkout.continued` ("<store> · Working", "your approval or answer reached the store") so Grok Bot picks the checkout back up and follows it without the user having to tell it; held off while Grok Bot is following the run itself. Logs carry a short SHA-256 user tag and the run's last six characters so one checkout can be traced.

- Setup from Grok Bot: the user says "Turn on Menta updates" (`UPDATES_PHRASE`), and the Bot calls `grok_bot_updates_setup`. The Bot can't see a routine's webhook URL or key (only the user can, in the routine's panel: "Webhook URL", "Webhook key" and a ready-made "Authorization header"), so the tool splits the work: it returns whether updates are on for this user (`updates`: `on`, `off` for saved but turned off or a key that must be pasted again, `none`), `accountUrl` (`/settings#grok-bot`), the routine to create (`routine`: name "Menta updates" and `ROUTINE_INSTRUCTION`, the same text the account page shows) and a `next` line: create the routine with that instruction, add a webhook trigger, then ask the user to open the routine's panel and paste the Webhook URL and key (or the header) at `accountUrl` and press Save, never in chat. Read-only annotations; no secrets in or out. It exists only for Grok Bot (clients.ts) and only where the server has Grok Bot updates: the one case where being Grok Bot changes which tools a client gets.
- Setup on `/settings#grok-bot` ("Grok Bot updates", under Connected assistants). Not set up: it leads with "In Grok Bot, say: Turn on Menta updates" with Copy, then two fields, Webhook URL and Key (the key field also takes the pasted `Authorization: Bearer …` or `Bearer …` header, quoted or not; `routineKey` strips it to the key), and Save; the full instruction and manual steps sit behind a collapsed "Set it up by hand". `PUT /api/grok-bot` (session user, same-origin) checks the URL like an MCP Events callback (`callbackProblem`: https on 443, no credentials, public host), accepts the key (8 to 512 printable characters), seals it with the MCP Events scheme (AES-256-GCM, HKDF from `STYTCH_SECRET`, its own purpose `grok-bot-routine-key-v1`), keeps its last four, and then sends the test right away (`{ event: "test" }`); the reply carries the test's outcome, shown inline ("Grok Bot got the test …" or why not). Set up: a compact "Grok Bot updates · On" with the key's last four and the last delivery's time and result ("Last sent 2 min ago · Delivered", or Refused / Not delivered, from `last_delivery_at`, `last_attempt_at` and `last_error`), and Send a test (`POST /api/grok-bot/test`), Turn off/on (`PATCH`) and Remove (`DELETE`); Replace URL and key appears only after a failed delivery or test. The key is never returned or logged.
- Offering it. While the user hasn't turned updates on, Grok Bot's payment and private-details lines end with: they can say "Turn on Menta updates" (then call `grok_bot_updates_setup`). For a user who never set them up, the first checkout Grok Bot starts carries a one-time offer: `grokBotUpdates: "off"` and a `next` suffix asking the model to add, once, "Want me to let you know here when a checkout needs you, even after this chat? Say 'Turn on Menta updates'." Once per user across clients and instances: `grok_bot_offers` (migrations/0007, user and time; an `INSERT … ON CONFLICT DO NOTHING` decides), also marked when the Bot calls the setup tool. The plugin's setup skill has a Grok Bot-only step that offers the same. There is no post-connect page to add a line to: our consent page hands straight back to the assistant after Allow, and the consent screen can't tell Grok Bot from Cursor's editor (both are Cursor clients), so nothing was added there.
- Updates are a backup, not a reason to stop. A model that stops following because updates are on can miss a question that arrives after the follower's window. So every `next` line for a running checkout says to call `continue`, whether or not updates are on.
- Which checkouts: the ones Grok Bot follows. Its own tool reads (`readByBot`, through `observeCheckouts` in the endpoint) adopt a run into the user's row and record its state and the time Grok Bot read it; they never push, since Grok Bot already knows. Other reads (the secure page and dock through `/api/checkouts/[runId]`, and followers) call `observe`: an adopted run whose state key (`status:requestId`, as for MCP Events) moved into needs-you, order placed or ended is sent once. While Grok Bot read the run in the last 30 s it is following it itself (its wait returns within seconds and it tells the user), so nothing is pushed. Once per state across instances: a compare-and-set on the row's `seen` entry (`claim`, which also re-checks Grok Bot's last read); a failed delivery sets it back.
- Delivery: one POST `{ source: "oca", event, ...MCP Events data }` with the Bearer key over the same SSRF-safe transport (public-only resolver, 10 s, no redirects): runId, store, task, status and headline in the dock's words, the question with its fields and options, the payment amount, the outcome, and `url` = `/checkouts/<runId>?via=grok`. Never the live view, progress, an order intent or the key. Up to 3 attempts (408, 425, 429, 5xx, network); a refusal (other 4xx) is recorded (`last_error`, shown on the account page) and not retried.
- The clock. Crossmint has no run webhooks, and there is no job runner. Every read of an adopted run (Grok Bot's tool calls, the secure page, the dock, and the approve or answer POST) also starts a follower in that request's `after()` (`follow`): it reads the run every 5 s (15 s after 5 minutes) and passes each view to `observe`, until the run settles and its update went out, updates are off, or the request's budget ends (50 s; the MCP and checkout routes have `maxDuration = 60`). One follower per run: a lease in the row (`watches`: chain and expiry, taken by compare-and-set). So Grok Bot hears what happens within about a minute of the last read on any surface, at no extra cost: the requests were running anyway.
  - Re-arming (off by default, `OCA_GROK_BOT_WATCH=rearm`): a follower that runs out of time while the run is still going hands over to a fresh invocation by POSTing a signed token (HMAC under a key derived from `STYTCH_SECRET`; user, run, chain, start, 1-minute expiry) to `/api/grok-bot/watch` (`maxDuration = 300`, follows for 280 s), which keeps the lease's chain. Capped at 30 minutes per checkout from the first read. This is what covers "the order went through 5 minutes after I approved" and a store question after Grok Bot's turn ended. Cost: a function kept alive (mostly idle, waiting on Crossmint) for up to 30 minutes per watched checkout, plus a Crossmint read every 5 to 15 s and a Neon read every 15 s and lease write per link while it runs, so Neon stays awake only during a watch.
  - Rejected: Vercel Cron (once a day on Hobby; every minute on Pro would read Neon every minute and keep it awake around the clock), and Crossmint's message stream (`/messages/stream`) on its own (still needs something to hold the connection; a follower could use it instead of polling later).
- Storage: `grok_bot_routines` (migrations/0006, `last_attempt_at` from 0007): user, URL, sealed key, last four, on/off, `seen` (run → state key, time, last Grok Bot read; entries older than 7 days are dropped), `watches` (leases) and delivery status (last success, last attempt, last error). `grok_bot_offers` (0007): who was offered updates. Off switch for the whole feature: `OCA_GROK_BOT_UPDATES=off`.
- The routine instruction (one source, `ROUTINE_INSTRUCTION`: the setup tool and "Set it up by hand"): read the checkout with `history`, ask the store's question with its question UI listing the options exactly and answer with `answer`, for a payment or private details say why in one line and send the body's url, after `checkout.continued` follow it with `continue`, report outcomes in one line, never approve payments, and treat `event: "test"` as a test.

Native host forms (`src/mcp/forms.ts`): MCP elicitation through multi round-trip requests (MRTR, protocol 2026-07-28). A tool returns `resultType: "input_required"` with one embedded `elicitation/create`; the host asks the user and calls the same tool again with `inputResponses` and our `requestState`. Nothing is stored: the retry carries the same arguments and the checkout is read again from Crossmint.

- Who gets it: forms are a fallback, not the main surface; our card is one UI wherever it can be drawn, and it handles questions, payment and private fields. A host that shows our card never gets a form or a link, even where it declares elicitation: ChatGPT, Claude and local MCP Apps hosts (`host` known), and any client declaring the MCP Apps extension (`io.modelcontextprotocol/ui`); the same `cards` rule as above. For the rest, only a request whose `_meta["io.modelcontextprotocol/clientCapabilities"]` declares `elicitation` (form mode for forms, `url` for links), and only when the server has a state key. 2025-era clients never do, even if their `initialize` declared elicitation: we serve them statelessly, so the per-request server never saw `initialize`, and the answer to a server-to-client request would come back as another HTTP request, possibly to another instance (the SDK's legacy shim refuses for the same reason). Claude Code negotiates 2026-07-28 with us and declares form and URL elicitation, so it gets both. OpenAI forms (`x-openai-suggestions`, `x-openai-thumbnail`) only go to clients that declare both `elicitation.form` and `extensions["openai/elicitation"].form`, as OpenAI requires for forms over MRTR, and their schema travels in `_meta["openai/elicitation"].requestedSchema` beside an empty core `requestedSchema` (OpenAI MCP Extensions 0.2.0; a schema in the core field is reported unsupported and never shown). Everyone else gets exactly the old results and `next` lines.
- `requestState` is the SDK's HMAC codec (`createRequestStateCodec`), keyed by HMAC-SHA256 of `STYTCH_SECRET` with a fixed label (`formStateKeyFromEnv`; no new secret), bound to the token's user and the method, 30-minute TTL. Its payload names the form (`question` or `secure`, with `runId` + `requestId`); it is signed, not encrypted, so it never holds an answer or address. A forged, expired or other user's state is refused (-32602) before the tool runs; `inputResponses` without our state for exactly this form are ignored and the form is asked again.
- Store questions: `answer` with only `runId` (the `next` line says so to clients that can). The form mirrors the dock: the store's question as the message, each field by its label, choices as `oneOf [{ const, title }]` (multi-select as `items.anyOf`), booleans as Yes/No choices (as in the dock, so "not answered" stays possible), text with its placeholder as the description, and "Something else" ("Tell the store what you want instead") last. No field is marked required, as in the dock: Something else replaces the answers, and the server checks the store's required fields and options on the way back, asking again with the problem first ("Answer Size, or tell the store what you want instead under Something else.") and the user's entries as defaults. OpenAI clients get the options as `x-openai-suggestions` instead, so the user picks or types; a typed value is Something else, sent as `{ alternative }` with every field the user filled. `x-openai-thumbnail` is drawn only for an https option image, and Crossmint's options carry none today. The result's `next` starts with "The user answered <store> in the form (Medium)." like the dock's note. A closed form sends nothing; answers for a question the card already answered aren't sent (the `requestId` check). `get_checkout` never asks: the card calls it every few seconds.
- Never in a form: payment, `protected` requests, and ordinary fields that look secret (masked input, password or one-time-code autofill: `QuestionField.sensitive`; or a label such as password, PIN, CVC, card number, verification code). Those stay in the card or the secure page. For payment and protected requests a client that declared URL elicitation gets `mode: "url"` to `pending.actionUrl` (for payment the spending limit request page, see above; for private details `/checkouts/[runId]`, `via` tagged), with "Approve a spending limit of 31.20 USD for Store on Menta. Your assistant never sees your card." Accepting only means the user agreed to open it; the tool returns the current checkout right away, and approval still happens only in Crossmint's UI on that page.
- Where the flow differs from the dock, and why: the form can't hide Something else behind a link or disable Send until an answer is ready, so Something else is always an optional last field and the server enforces what the dock's button did. Country is a list of names, and the region/postal labels follow the starting country until the user's choice comes back with a problem. Forms go only to card-less clients that declare elicitation (Claude Code, Codex, Cursor; see [HOSTS.md](HOSTS.md)); URL elicitation to the secure page is their payment and private-details fallback.
- Why ChatGPT doesn't get its own forms: we tried store questions in ChatGPT's native form (October 2026) and went back to the card. The card is the same UI as the dock in every host, and ChatGPT's forms behaved differently by surface: Work on the web declined them unseen, the desktop app's Chat declares none, and the desktop app's Work with Full access accepted them empty without showing them; only Work with "Ask for approval" showed them. A form answered while the model waits also left the model out of the conversation.

Card versions: hosts cache an MCP Apps view by its URI (ChatGPT kept showing the old card after a deploy and a tool refresh), so the card is served at `ui://oca/checkout-<12 hex of its HTML>` and tools point there.

Display modes in the card:

- Display modes: the resource carries `openai/ui.availableDisplayModes = ["inline", "fullscreen"]` (ChatGPT has no pip) and `ui/initialize` declares `["inline", "fullscreen", "pip"]`. The card asks only for modes the host lists (ChatGPT's own `requestDisplayMode` without a list counts as inline and fullscreen; pip is never offered on ChatGPT). The pure rule is `modeOffers` in `card/model.ts`: "Expand" (fullscreen) and "Keep visible" (pip) for an active checkout, "Back to chat" out of them, nothing for a superseded card. When the secure step opens on a phone (`hostContext.platform` or ChatGPT's `userAgent.device.type` is mobile), the card asks for fullscreen once per request. `hostContext.safeAreaInsets` pad the card; fullscreen lays it out as a centered column.
- Live updates: a card that can't call our tools (no `serverTools` from `ui/initialize` and no `window.openai.callTool`) doesn't promise updates: it shows the status as of the result and "See live progress on Menta". It still probes one `tools/call` (some hosts answer without advertising it) and re-checks after 1.5, 5 and 15 s and on context changes. Being out of view slows polling (×5) instead of stopping it. A card that can't follow an active checkout (or hasn't read it for 30 s) calls the app-only `card_diagnostics` once per reason (`no-server-tools`, `initialize-failed`, `tools-unadvertised`, `stalled-frozen`, `stalled-paused`, `stalled-hidden`, `stalled-unknown`), which logs the reason, the host and the host's name in plain words only, so server logs show which case a host is in. Only the newest card for a run reports stalls.

Auth: every request needs a Bearer token. Stytch Connected Apps tokens are verified locally (issuer = project domain, audience = project ID + `{origin}/mcp`, required scopes, capped lifetime); their subject is the Stytch user, so the Crossmint user is the same as on the web. A missing or rejected token gets `401` with `WWW-Authenticate: Bearer resource_metadata="{origin}/.well-known/oauth-protected-resource/mcp"`, whose document names the Stytch project domain as the authorization server; clients take discovery (RFC 8414), client registration and tokens from Stytch. Stytch advertises both Dynamic Client Registration and client ID metadata documents (`client_id_metadata_document_supported` plus the `none` auth method), so ChatGPT and Claude connect with CIMD and others with DCR. Browser requests from other origins are refused. Under `next dev` on a loopback origin only, a Stytch web session token is also accepted as the Bearer so local MCP clients work before OAuth is set up; it is off in builds, on Vercel and on non-loopback origins.

Plugin settings (`src/mcp/settings.ts`; OpenAI MCP Extensions "Structured Settings"): `/settings` inside ChatGPT's plugin settings, with the same sections, labels and copy. The server advertises `capabilities.extensions["openai/settings"] = { readTool: "settings_read", updateTool: "settings_update" }`, plus the legacy `experimental` key. One `registerCapabilities` call covers both `server/discover` (2026-07-28) and `initialize`. `settings_read` takes `{}`, declares an `outputSchema`, and returns one property, `defaultAddress`: a string `enum` of the saved labels plus "None" ("No default" if an address is labelled None), titled "Default for my deliveries". The layout has three groups. "Cards · saved by Crossmint" holds "Manage cards". "Addresses" holds the default and "Add an address". "Store sign-ins" holds "Sign out of all stores", and its description says whether stores remember the user. `settings_update` takes `{ set: { defaultAddress } }` and calls `setDefaultAddress` for that label, or clears the default for None, the same as `PATCH /api/addresses/[id]`. The two link buttons are MCP App tools. ChatGPT shows their small view (`ui://oca/account`, `src/mcp/account-view.ts`, no network, links only to our origin) in a modal. The view opens `/wallet#cards` or `/addresses#add-address` (which opens the add form) through `ui/open-link`, falling back to `openExternal` and then a new tab. Card entry never moves into the host's settings. "Sign out of all stores" is a regular tool (`clearSignIns`, like `DELETE /api/store-sign-ins`), and its result line becomes ChatGPT's tooltip. Every settings tool is registered only for ChatGPT and local dev (`offersSettings`), and `settings_read`, `settings_update` and `settings_sign_out_stores` are app-only: these controls are the user's, so no model, including one in a host that ignores `ui.visibility`, can call them (the model changes the default only through `set_default_delivery_address`, when the user asks). The two link tools stay visible to the model, because ChatGPT won't render a private tool's view in settings; they only return a link to our own pages. No button tool declares an `openai/ui` settings entrypoint: OpenAI removed those in mcp-extensions 0.2.0, and ChatGPT drew no buttons while ours declared one. Values are labels only, never profile IDs, streets or names.

Plugin package (`plugins/menta`, `apps/web/lib/plugin.ts`): the MCP server packaged with a `setup` onboarding skill (`extensions["com.openai"].onboardingSkill`) and a `buy` skill that is the server `instructions` verbatim. It has the portable `plugin.json`/`mcp.json` for ChatGPT and Codex, `.claude-plugin/plugin.json`/`.mcp.json` for Claude, and `.cursor-plugin/plugin.json` for Cursor and Grok Bot (the Cursor Marketplace; logo by relative path, `skills/`, the MCP server inline by URL), with the repo-root `.cursor-plugin/marketplace.json` pointing at the folder, plus the mascot as its logo (`apps/web/public/brand`). `pnpm plugin:sync` writes the derived files, and a unit test fails when they drift. Local install steps are in the package README.

User-scoped state belongs to the Stytch user, not an MCP session (the server keeps none).

## Memory

`agent/memory.ts` declares an Eve memory slot with a small Neon-backed provider (`src/memory-provider.ts`). Eve automatically recalls all notes before every turn, including the first turn of a new conversation, and again after compaction. A stable recall message ID replaces old context, including with an explicit empty record after notes are cleared. Scope comes only from the verified Stytch user; anonymous and local runtime callers have no memory, with no shared development fallback.

The model decides what to save as concise free-form notes through `memory__save_memory` and what to forget through `memory__remove_memory`. There are no preference categories or automatic transcript ingestion. Notes are user data, never instructions or payment authorization; current requests override them. Secrets, protected inputs, capability URLs and payment approvals must never be saved. Addresses and purchase state stay in Crossmint.

`user_memories` (migration 0008) holds each user's notes with stable UUIDs and a version. Optimistic updates retry conflicts, deduplicate identical saves, and preserve simultaneous saves and deletions. Recall is bounded to 8,000 characters, with at most 2,000 per note; exceeding the limit returns an error so the model can remove outdated notes instead of silently losing information. The store is shared between web chat and MCP and survives restarts.

Memory belongs to the web chat only; the MCP server has none (assistant hosts keep their own). The web app has no page for it: the model saves and forgets notes when asked, and deleting a conversation leaves memory intact. An existing turn can retain previously recalled notes until its next turn.

Sign-in: Stytch sends the assistant's OAuth request to `/oauth/authorize`. The page requires the web session (via `/login?next=…`, including Google), calls Stytch `idp.oauth.authorizeStart` through the project domain (so the redirect's `iss` is the advertised issuer), shows consent, and submits the decision with `idp.oauth.authorize`, then follows Stytch's redirect back to the assistant. `/connections` lists and disconnects connected assistants through Stytch.

## State

Crossmint is the source of truth for checkouts, cards, receipts, saved addresses and store sign-ins. Addresses are Crossmint buyer profiles (shipping and contact, each with a `label` such as "Home"; no per-user cap), listed, added, edited and deleted on `/addresses`. Crossmint has no default flag, so Neon keeps `user_id → buyer_profile_id` (`default_addresses`): the user's own place, set only when they choose it (no row, or a deleted profile, means no default). Every checkout create says how it's fulfilled (`fulfillment`: `delivery`, `pickup` or `none` for tickets and digital goods) and, for a delivery, whom it's for (`deliverTo`: `me`, `store_account` or `someone_else` with `addressLabel`). `planShipping` decides what to attach (we send no merchant guidance, so Universal Checkout's own applies); see [ADDRESSES.md](ADDRESSES.md). Only a delivery to someone with no saved address starts nothing (`needs_address`); a delivery to the user without a default starts with nothing attached, and the store account or the store's question covers it. The signed-in agent can read complete saved buyer facts through `checkouts__addresses`: profile ID, label, place, default flag, recipient name, contact email and phone, and complete shipping address. It reads these on demand for relevant user requests and ordinary store questions, using the default or explicitly named recipient and giving current instructions priority. Both tools share one projection; profiles remain in Crossmint and never authorize payment. Checkout views carry `shipsTo: { label, place }` for the run's `buyerProfileId`, resolved with one buyer-profile list per read (a failed read only drops the line); the web card, the dock's payment step and the in-host card show "Ships to Home · Miami, FL". Each checkout also attaches the user's single browser profile (created on first checkout, cleared from `/settings`) so store logins carry over. Eve keeps conversations and durable task state. Neon stores `session_id → owner, title`, the default address ID, free-form user memory notes, MCP event subscriptions (what we last told each one, not checkout state), whether each MCP client draws cards (and its name), and each user's Grok Bot routine (URL, sealed key, what we last told it). A completed agent turn is never treated as a completed purchase.

Deleting an account (`DELETE /api/me`, same-origin, verified session only) cancels the user's active approvals, removes their cards, addresses and store sign-ins at Crossmint, deletes every Neon row keyed to them (`forgetUser` in `@oca/agent/forget-user`, one place for every per-user table), and last deletes the Stytch user, which revokes their sessions and connected assistants. Each step is idempotent; the first failure stops with a 502 so a retry finishes it. Crossmint keeps its checkout runs and purchase history, and Eve keeps conversation transcripts, which nobody can open once the owner rows and the Stytch user are gone.

## Desktop notifications

Users opt in from a small "Notify me" action in the active checkout dock; `/settings#notifications` also exposes the enable, test and off controls. The browser registers `/notifications-sw.js` and stores a Web Push subscription through `/api/notifications`, derived from the verified Stytch user. The endpoint accepts only known browser push providers; endpoints and encryption keys are sealed with the existing secret box under a distinct `STYTCH_SECRET`-derived purpose (migration 0009). No subscription capabilities reach the model or logs.

`readCheckout` in the existing durable Eve `watch_checkout` task delivers attention and outcome notifications for web checkouts after verifying the original chat owner. Working polls add no notification storage reads or Crossmint calls. A per-device/run/request delivery claim deduplicates retries and restarts; claims older than seven days are pruned on the next delivery read. Enrollment uses a per-user transaction lock to enforce the 20-device cap under concurrency. Transient push failures get one bounded retry, expired subscriptions are removed, and delivery failures never prevent the agent from receiving checkout state. There is no additional scheduler or checkout state machine.

Checkouts an assistant host started (ChatGPT, Claude, Grok Bot) have no Eve watch. The MCP endpoint (`push` option, `pushingCheckouts` in `src/mcp/endpoint.ts`) checks the single reads the host makes (start, status, waits, its card's polling) and, while the checkout needs the user (a pending question, private step or payment), delivers through the same claims. These notifications open the run's secure page instead of a conversation: `/checkouts/<runId>?via=<host>`. Lists never push (old runs are not news), and outcomes stay in the host. Nothing is sent while no surface reads the run.

The worker only handles push and notification clicks; it never caches or intercepts authenticated pages. Notifications name the payment merchant when available, otherwise the store domain, and describe the required action or outcome. Ordinary questions use fixed categories derived from recognized field labels (for example, drink size, color or delivery method); unknown questions fall back to a store-specific prompt. Masked fields and secret requests use the secure-details prompt. No task, raw question, option value, address, contact detail, result summary, payment credentials or capability URL is copied into the preview. Formatting adds no model call or provider read. Clicks focus/open the original `/c/<sessionId>` so dock responses resume the same durable watch. Expired action copy becomes a generic update. Closing tabs is supported; browser/OS notification permission and background delivery still apply. Enrollment also sets an HttpOnly device hint, so every logout surface deletes that device for the verified outgoing user before revoking the session; the cookie itself grants no authority. Account, checkout and consent switch flows unsubscribe the browser. Provider renewal events refresh only an endpoint already owned by the signed-in user; signed-in visits compare endpoint digests and repair renewals, while expired provider subscriptions are recreated on explicit enable. A revoked permission still leaves the off control usable. Missing VAPID configuration leaves the setting unavailable.

## v2: goals (proposed, for sign-off)

v2 reorganizes both apps, the web and the phone, around one main chat that starts *goals* (working name). Each goal is its own conversation with its own agent, and Crossmint checkouts are its steps. The design is the "v2 · Reset: home in v1 style" page on the design canvas; this section is how it fits the system. Ownership doesn't change: Eve keeps conversations and durable waits, Crossmint keeps checkouts, cards and payment authority, and we keep a small record per conversation. Still no order ledger, checkout state machine or job runner. Approval, cards, the Visa and Mastercard checks, secure fields and the live view stay as they are.

**Conversations.** Every user has one *home* conversation and any number of *goal* conversations. Both are ordinary Eve sessions on the same root agent, so a goal is a chat the user can open and talk to directly. We don't use Eve subagents for goals: a subagent is a task inside its parent's turn, with no conversation the user can open or come back to weeks later. `web_session_owners` (migration 0012) gains `kind` (`home`, `goal`, or `chat` for conversations from before v2), `parent_session_id` (the home that started a goal), `event_date` (the date a booked goal is for, such as a trip's check-in, when there is one), `last_activity_at` and `done_at`. The title is the goal's name ("Peru trip"). One home per user, created on first sign-in after v2 ships. It is long-lived: Eve compaction and memory keep its context bounded.

Sessions currently end 30 days after they are created (Eve's default `limits.sessionTimeoutMs`), which also applies to today's chats. Goals can last longer than that, so v2 sets `sessionTimeoutMs: false` in `agent/agent.ts`. Token and cost limits per session still apply.

**Starting a goal.** In home, the agent calls a new `start_goal` workflow tool with a name and a brief (everything the goal's agent needs, since it doesn't see home's history). The tool creates the goal's Eve session on our own runtime with the brief as its first message, binds it to the same verified user with `kind: goal` and the parent, and returns the goal's ID for home to link ("Started Peru trip"). Creating the session server-side means the goal starts even if the user closes the app. The web channel (`src/web/channel.ts`) accepts that request through a short-lived credential: an HMAC over the user, the parent session and a timestamp, keyed from `STYTCH_SECRET` with its own purpose and checked like the bearer and cookie paths, never derived from caller input. Home also gets `list_goals` (to answer "how's Peru going?") and `message_goal` (to pass an instruction typed in home on to a goal). A goal's agent gets the same commerce tools as today's chat plus `finish_goal` (marks it done; its final message is the summary card), `set_goal_date`, and `message_home`, so a goal can talk to the main chat too: to report something that matters beyond the goal ("the Peru dates moved to the 22nd"), or to ask home about another goal or what the user said there.

Messages between conversations go through the same signed server-side request as `start_goal`, into the other session as an ordinary turn, so the receiving agent can act on them. They are marked with where they came from: the chat shows them as a quiet line ("From Peru trip: …"), and the receiving model sees them as a message from another of the user's goals, never as the user. They carry no authority the user didn't give: a relayed message can't approve anything (approval stays in Crossmint's UI), and agents are told not to answer a relayed message with another relay unless the user needs to know. Each conversation can send a few per hour, so two agents can't loop. A dynamic instruction block, picked by the session's `kind`, tells each agent which role it has. Small asks still become a goal with one step, so there is one model, not two.

**Goals and their checkouts.** Crossmint runs can't carry a goal ID today. We record `(session_id, run_id)` in `conversation_runs` (migration 0012) from an Eve hook on `action.result` for `checkouts__create`, idempotent on the pair, so the index is written where the run is started, at least once. The same hook also records runs in today's chats. Checkouts started before rollout have no rows: a one-time script at rollout (`scripts/backfill-conversation-runs.mjs`) replays each owned session's Eve history, takes the run IDs from its `checkouts__create` results and writes the same rows. It is a migration step, run once, not a recurring job. Until it has run, an older chat shows as done. If Crossmint adds an external ID or metadata field to runs, we pass the session ID there and drop the hook; we'll ask for it.

**The overview.** `GET /api/goals` (signed-in, uncached) returns the user's goals with their state, read for the verified user only:
- the goal record;
- for each run in `conversation_runs` that is still active, the Crossmint view (one read per active run, in parallel, through the same projection as `/api/checkouts/[runId]`, so no capability URLs or secrets);
- a derived state per goal: **needs you** (a run waiting on a question, private step or payment), **going on** (a run working), **paused** (no active run and no activity for a day), **coming up** (done, with an `event_date` more than two days away), **done**.

States are derived when the overview is read, not stored or scheduled. A coming-up goal moves back to home by itself when the date gets close because the next read says so. Runs that have ended read nothing. Checkouts started in ChatGPT, Claude or Grok Bot that are waiting on a payment approval or a private step appear in the same overview as items without a goal (from `runsNeedingYou`), opening their checkout screen (`/checkouts/[runId]`). A plain store question from those checkouts stays with the host that asked it: its agent relays the answer, as today, and the overview doesn't show it. Home shows the first three; the menu lists all of them by state. A goal page shows all of its runs, ended ones included: it reads every run in `conversation_runs` for that goal through `/api/checkouts/[runId]`, and the client keeps an ended run's view for the session, since it can't change. Ended steps and their details (placed, stopped, expired and why) come from that view, and the goal's conversation still has each step's outcome card. What changed since an expiry, such as a new price, is the agent's message in the conversation, not something the overview stores. The overview replaces the per-chat dock as the place store questions and payments wait; several open at once step through one sheet ("1 of 2"). The sheets are today's forms, and answers still go to Crossmint through `/api/checkouts/[runId]`, never through the model.

**Long-lived goals.** A checkout that expires leaves its step saying so and what changed, when known. There is no restart button: the user tells the goal's agent in the conversation, and it starts a fresh checkout. "Paused" and "coming up" are derived as above. Each goal session keeps its own `watch_checkout` task, so it wakes its agent and sends push exactly as today's chats do. Notifications open the goal (`/c/<sessionId>` keeps working: that path becomes the goal page) and are sent only for "needs you" and outcomes, as now. A Live Activity for the checkout that needs the user comes later, once the app can send APNs updates through an Apple team.

**The web follows.** The web home becomes the main chat with the overview above the composer, the sidebar becomes the goal menu (needs you, going on, coming up, done), and `/c/[sessionId]` is the goal page. Conversations from before v2 (`kind: chat`) show as goals in the menu, with their state derived the same way, and open as they do today; nothing is migrated. The MCP server for ChatGPT, Claude and Grok Bot doesn't change: those hosts keep their own conversations, and their checkouts show in the overview.

**What changes in the code.**
- Server: migration 0012, the channel's goal credential, `start_goal`, `list_goals` and `message_goal` (home), `message_home`, `finish_goal`, `set_goal_date` and `set_goal_plan` (goals), the runs hook, the backfill script, `GET /api/goals`, `sessionTimeoutMs: false`, role instructions by `kind`.
- Shared (`@oca/client`): goal state derivation and the overview's ordering, used by both apps so they never disagree.
- Web and app: home with the overview, the goal menu, the goal page, and the stepping sheet; the dock moves into the overview.

**Rollout.** Server first, behind `OCA_GOALS=on` so today's chats keep working. The backfill runs once per environment after migration 0012 and before `OCA_GOALS` is turned on there, so older chats show their steps from the first read. Then the app, then the web, each switched on together with its UI. The Live Activity comes last.

**Decisions (2026-10-17, defaults the owner can revisit).**
- No generic word for a goal on screen: goals show their own names ("Peru trip") and the sections say "Needs you", "Going on", "Coming up", "Done". The code says *goal*.
- Goals keep a small plan: `set_goal_plan` writes a short ordered list of steps (a label each, at most eight), so a goal shows "flight · hotel · ride" before its checkouts start. When the agent starts a step's checkout it writes the plan again with that step's `runId`, so the goal shows each step's live state. The plan is the agent's intent, never a promise of price or availability.
- Store choices show exactly as Crossmint sends them. A display-only tidy layer can come later, with the original text one tap away.
- We'll ask Crossmint for an external ID or metadata field on runs, which would replace the runs hook. Until then the hook is the source.
